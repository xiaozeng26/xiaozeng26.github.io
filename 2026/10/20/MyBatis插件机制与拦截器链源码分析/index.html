MyBatis插件机制与拦截器链源码分析

引言

做过几年业务系统的同学，大概率都遇到过这样的需求：想给所有 SQL 统一加上租户条件、想统计每条 SQL 的耗时、想对敏感字段做脱敏、想在分页时自动改写 SQL……这些需求有个共同点——它们都发生在 SQL 执行的前后，但你不想改业务代码，也不想改 MyBatis 源码。

这时候，MyBatis 的插件机制（Plugin）就派上用场了。分页插件 PageHelper、SQL 监控插件 p6spy 的 MyBatis 集成、数据权限插件，几乎都是基于这套机制实现的。

但真正读过源码的人会发现一个问题：你明明传了一个 Interceptor 进去，为什么它返回的 Executor 却变成了一个 Plugin 对象？ 更迷惑的是，Plugin 类实现了 InvocationHandler——它居然是个动态代理！也就是说，MyBatis 的插件本质是 JDK 动态代理的一层"马甲"。

这篇文章我们从一次生产事故讲起，然后一路挖到 Plugin.wrap() 和 InvocationChain 的源码，把整条拦截器链彻底讲透。读完之后，你不仅能写出正确的插件，还能避开那些"插件一多就乱序""拦截不到嵌套查询"的坑。

核心概念：餐厅后厨与"中间人"

先打个比方。

想象一家餐厅的后厨，主厨（Executor）负责真正炒菜，但餐厅里还有几类角色：采购员（StatementHandler，负责拿食材）、配菜员（ParameterHandler，负责处理调料）、摆盘师（ResultSetHandler，负责装盘）。

现在老板（业务方）提了个需求：每道菜出锅前都要过一遍质检。你不想让主厨改流程，也不想让采购员分心。于是老板安排了一个"质检员"站在主厨和点单台之间：所有点单先经过质检员，质检员可以看一眼、记个时间、甚至偷偷改一下订单内容，然后再转给主厨。

这个"质检员"就是 Interceptor（拦截器）。而站岗的岗位——主厨、采购员、配菜员、摆盘师——就是 MyBatis 允许你拦截的四个核心接口。

技术上讲，MyBatis 插件机制由三部分组成：

  1. Interceptor 接口：定义 intercept(Invocation)、plugin(Object)、setProperties(Properties) 三个方法。
  2. @Intercepts + @Signature 注解：声明你要拦截哪个类的哪个方法，参数类型是什么。
  3. Plugin.wrap()：把目标对象包成 JDK 动态代理，代理的 InvocationHandler 就是 Plugin 本身。

关键点在于：拦截器不是"链式调用"的，而是"套娃式"的。多个插件会一层层包裹，最外层的插件先执行，最后才是真实目标对象。

这里有三个细节值得深挖：

细节一：getSignatureMap 解析注解。 它把 @Signature 的 type、method、args 组合成 Method 对象，放进以接口类为 key 的 Map。注意 Method 的构造可能抛 NoSuchMethodException，如果注解写错了方法名或参数类型，启动时就会直接抛异常——这其实是好事，早失败早暴露。

细节二：getAllInterfaces 只返回"被拦截的接口"。 比如你只拦截 Executor，那么 CachingExecutor 实现的 Executor 接口会被返回，但 CachingExecutor 自己的类不会被代理。这意味着你无法拦截目标类的非接口方法——这是 JDK 动态代理的固有局限，不是 MyBatis 的锅。

细节三：没有匹配接口时返回原对象。 所以一个插件如果签名写错，不会报错，而是"静默失效"。这是最常见的坑之一。

3. Plugin.invoke：拦截器链的真正执行者

Plugin 实现了 InvocationHandler，所有代理方法调用都会进入 invoke：

注意 method.getDeclaringClass() 这一行。假设你拦截 Executor.query，而 CachingExecutor 重写了 query，那么 method.getDeclaringClass() 是 CachingExecutor 还是 Executor？答案是取决于方法在哪个类中声明。如果 CachingExecutor 自己声明了 query，getDeclaringClass() 就是 CachingExecutor，而你的 signatureMap 里 key 是 Executor——匹配不上，拦截失效！

这是 MyBatis 插件最阴险的坑之一。实际上 CachingExecutor 确实重写了 query，但 signatureMap 的 key 是注解里写的 Executor.class。那为什么 PageHelper 能拦到？因为 getSignatureMap 里对 @Signature.type 用的是接口类，而 CachingExecutor.query 的 declaringClass 是 CachingExecutor……等等，这里需要澄清：Method.getDeclaringClass() 返回的是方法"首次声明"的类。CachingExecutor 的 query 是它自己声明的（重写），所以 declaringClass 是 CachingExecutor。那匹配岂不是必然失败？

实际源码里 getSignatureMap 用的是 type.getMethod(...)，得到的 Method 的 declaringClass 就是 type 本身（接口）。而代理对象调用时传入的 method 是接口方法（因为 Proxy.newProxyInstance 传入的 interfaces 是接口数组），所以 method.getDeclaringClass() 返回的是接口。这就是为什么 getAllInterfaces 只返回接口、Proxy 也只代理接口方法——保证 declaringClass 与 signatureMap 的 key 一致。理解这一点，你就明白 JDK 代理在这里为什么"必须"用接口了。

4. Invocation：拦截器手里的"接力棒"

proceed() 就是"把活交给下一棒"。但注意：它调用的是 target 的方法，而 target 是"下一个插件代理对象"或"真实对象"。所以当拦截器 A 的 intercept 里调用 invocation.proceed()，实际触发的是拦截器 B 的 invoke，B 再 proceed 到 C……最终到真实对象。这就是"责任链"的实现方式——用动态代理的嵌套调用模拟出链式效果。

方案对比：MyBatis 插件 vs 其他扩展方式

方案 原理 优点 缺点 适用场景
MyBatis 插件（Interceptor） JDK 动态代理 + 责任链 无侵入、可拦截四大对象、生态成熟 只能拦接口方法、顺序依赖注册、调试困难 分页、监控、多租户、SQL 改写
自定义 SqlSessionFactoryBean 包装 替换核心对象 完全可控 侵入性大、需理解初始化流程 深度定制
MyBatis-Plus 内置拦截器 官方实现 开箱即用、顺序管理 绑定 MP 生态 用 MP 的项目
AOP 切 Mapper 接口 Spring AOP 简单、可切业务方法 拿不到 SQL 上下文、无法改 SQL 缓存、日志
JDBC 层代理（p6spy） 驱动代理 与 ORM 无关 无法感知 MyBatis 语义 通用 SQL 监控

对比可以看出，MyBatis 插件的核心优势是能拿到 MappedStatement、BoundSql 这类 ORM 语义信息，这是 AOP 和 JDBC 代理做不到的。但代价就是前面说的"套娃顺序"和"只能拦接口"这两大限制。

最佳实践与避坑指南

1. 签名写错会静默失效，务必写单测验证。

@Signature 的 method 名或 args 类型写错，getSignatureMap 会抛 NoSuchMethodException（这是好事）；但如果 type 写的是一个目标对象没实现的接口，getAllInterfaces 返回空数组，wrap 直接返回原对象，插件静默失效。建议每个插件都写一个断言"代理对象是 Plugin 实例"的测试。

2. 拦截 query 要拦全参数版本。

Executor 有 query(MappedStatement, Object, RowBounds, ResultHandler) 和 query(MappedStatement, Object, RowBounds, ResultHandler, CacheKey, BoundSql) 两个重载。只拦前者，某些内部调用（如嵌套查询）可能走后者，导致漏拦。PageHelper 两个都拦。

3. 顺序管理用 @Order 或 order 属性。

Spring Boot 下多个 Interceptor Bean，注册顺序受 Bean 加载顺序影响，不可靠。推荐在 的 property 里显式声明顺序，或自定义 ConfigurationCustomizer 按 @Order 排序后手动 addInterceptor。

4. 不要直接在 intercept 里改 BoundSql.sql。

BoundSql 可能被缓存复用，高并发下会串 SQL。要改写 SQL，走 MappedStatement 替换或 SqlSource 重写路线，参考 PageHelper 的 ExecutorUtil。

5. proceed() 必须放在 try-finally 里。

否则异常路径下"退出"逻辑不执行，监控数据会失真。示例一的写法就是标准姿势。

6. 注意 plugin 方法的 instanceof 判断。

pluginAll 会对四大对象都调 plugin，虽然 wrap 内部会检查，但提前判断能省掉 getSignatureMap 的解析开销（虽然 InterceptorChain 对 signatureMap 没有缓存，每次 wrap 都重新解析注解，插件多时这是实打实的性能损耗）。

7. 嵌套查询（Nested Query）的拦截盲区。

ResultSetHandler 处理嵌套结果时，可能通过 Executor 内部再次查询，此时新 Executor 是否被代理取决于 MappedStatement 的 executorType。如果发现"插件对某些 SQL 不生效"，先检查是不是嵌套查询走了不同的 Executor 实例。

总结

把整条链路串起来：

  1. 装配：InterceptorChain.pluginAll 对四大对象依次调用 plugin，先注册的在内层。
  2. 代理：Plugin.wrap 用 @Intercepts 生成 signatureMap，对匹配接口做 JDK 动态代理。
  3. 执行：Plugin.invoke 命中签名则调 interceptor.intercept，拦截器内 invocation.proceed() 触发下一层代理，形成套娃式责任链。

核心洞察是：MyBatis 插件 = JDK 动态代理 + 责任链模式的嵌套实现。理解了"套娃"和"接口代理"这两点，顺序问题、失效问题、嵌套问题就都有了统一解释。

延伸思考：如果你要设计一个类似的扩展框架，MyBatis 这套方案给你什么启发？其实它牺牲了"非接口方法拦截能力"和"显式顺序控制"，换来了"零侵入"和"与 Spring 解耦"。现代框架（如 Dubbo 的 Filter、Spring 的 HandlerInterceptor）更倾向于显式链式结构 + 顺序声明，可调试性更好。MyBatis 受限于历史设计（JDK 代理），只能靠约定和文档来弥补。这也提醒我们：扩展点的设计，顺序可观测性和失败可见性，比"优雅"更重要。

下次再写插件，先问自己三个问题：拦的是接口方法吗？顺序想清楚了吗？proceed() 在 finally 里吗？想清楚这三点，坑就少了一大半。
