FastAPI + Tortoise ORM 异步数据库实践

引言

去年双十一前，我接手了一个用 FastAPI 写的订单查询服务。压测时 QPS 刚到 800 就上不去了，CPU 却只跑了 30%。打开火焰图一看，asyncio 事件循环里躺着大量 psycopg2 的同步阻塞调用——await db.execute(...) 表面上是异步的，底下却在用线程池硬扛，线程池一满，整个事件循环就开始排队。这就是典型的“伪异步”：你以为自己写的是 async，实际上只是把阻塞操作从主线程挪到了 thread pool。

这个问题的根子不在 FastAPI，而在 ORM 选型。FastAPI 本身是纯异步的 ASGI 框架，但如果你配的是 SQLAlchemy 1.4 的同步 Session，或者 Django ORM，那异步链路就在数据库这一层断掉了。Tortoise ORM 正是为填补这块空缺而生的：它是原生 async 的 ORM，API 设计上高度致敬 Django ORM，让熟悉 Django 的工程师几乎零成本迁移。

这篇文章不讲“怎么装包、怎么定义模型”这种入门内容。我们要往下钻：Tortoise 的连接池是怎么在事件循环里工作的？await Model.get() 背后发生了什么？它和 SQLAlchemy 2.0 async、asyncpg 裸用相比，各自的边界在哪？以及最关键的——生产环境里踩过的那些坑。

核心概念：从“餐厅后厨”理解异步 ORM

先把 asyncio 想象成一家只有一个传菜员的餐厅。

  • 同步阻塞模型：传菜员把菜端到后厨窗口，然后站在那儿等厨师做完。等的时候他什么也干不了。这就是 psycopg2 的行为。
  • 线程池伪异步：老板看传菜员老等着，就雇了 20 个传菜员（线程池）。每个传菜员照样站着等，但至少能同时等 20 单。问题是：传菜员是有成本的（8MB 栈 + 上下文切换），而且 20 个传菜员全占满的时候，第 21 单照样卡住。这就是 SQLAlchemy 1.4 同步 Session 在 async 环境下的真相。
  • 真异步：传菜员把订单贴到窗口就转身走人，厨师做完按铃，传菜员再回来取。一个传菜员能同时处理几百单。这就是 Tortoise + asyncpg 的模式——数据库驱动本身是非阻塞的，等待期间事件循环可以调度其他协程。

所以判断一个 ORM 是不是“真异步”，关键看底层的数据库驱动是不是非阻塞的。Tortoise 在 PostgreSQL 下用 asyncpg，MySQL 下用 aiomysql，SQLite 下用 aiosqlite——全部是原生异步驱动，没有线程池兜底。

Tortoise 的另一个设计取舍是放弃 Data Mapper、拥抱 Active Record。SQLAlchemy 是 Data Mapper：模型是纯 Python 对象，和 Session 解耦，Session 负责跟踪状态、生成 SQL。Tortoise 是 Active Record：模型类自带 save()、delete()、filter()，像 Django 一样。这个取舍在异步场景下其实更自然——因为异步里你本来就该“用完即走”，不需要长生命周期的 Session 去维护身份映射（identity map）。这一点后面会细说。

怎么选？我的经验是分三档：

  • 业务 CRUD 为主、团队有 Django 背景：Tortoise 最省心。它的 API 让你几乎不用思考“连接从哪来”，异步链路干净。
  • 领域模型复杂、需要多数据源、要成熟迁移：SQLAlchemy 2.0 async。它的 AsyncSession 虽然重，但 selectinload 控制加载策略的能力远超 Tortoise，大型项目后期会庆幸当初选对了。
  • 报表、批量导入、复杂聚合：直接 asyncpg。ORM 生成的 SQL 在这种场景下往往是负担，手写 SQL + conn.fetch() 反而更清晰、更快。

还有一个常被忽略的对比维度：Tortoise 的迁移工具 Aerich 相比 Alembic 是明显短板。它不支持自动检测所有 schema 变更（比如索引增删、约束修改），复杂迁移经常要手写 SQL。如果你的项目 schema 会频繁演进，这点要提前评估。

最佳实践与避坑指南

1. 连接池参数必须和 PG 的 max_connections 联动算

这是最容易出事的地方。假设 uvicorn --workers 4，每个 worker 一个进程一个事件循环一个池，池 max_size=20，那峰值就是 4×20=80 个连接。PostgreSQL 默认 max_connections=100，再算上运维连接，很快就 too many clients。经验公式：

宁可把 max_size 调小（比如 10），靠事件循环的并发能力扛，也别把连接数堆爆。

2. using_db(conn) 一个都不能漏

事务内所有 ORM 操作都必须显式传 using_db=conn。漏一个，那个操作就会从池里另借一个连接，跑在事务之外，回滚时它不跟着回滚——数据就脏了。这是我在 code review 里抓得最多的 bug。

3. 别在事务里 asyncio.gather

前面说过，asyncpg 连接单工，事务内并发写会直接崩。要并发，就在事务外并发，或者拆成多个独立事务。

4. 测试里的 asyncio.run() 是连接池杀手

pytest 每个用例 asyncio.run() 会建新 loop，而 Tortoise 的池绑在旧 loop 上。解决方案是全局一个 loop（pytest-asyncio 的 event_loop fixture），或者在 fixture 里每个用例 Tortoise.init + close_connections。我推荐后者，隔离干净。

5. N+1 查询一定要用 prefetch_related

Tortoise 不会自动预加载。user.orders 第一次访问会触发一次查询，循环里就是 N+1。养成习惯：列表接口返回关联数据时，先 filter(...).prefetch_related("orders")。

6. 深分页用 keyset，别用 offset

offset 100000 limit 20 会让 PG 扫描并丢弃 10 万行。用 filter(id__gt=last_id).order_by("id").limit(20)，走索引，O(1) 定位。

7. Decimal 字段别用 float 中转

balance 是 DecimalField，从 DB 读出来是 Decimal。如果经过 Pydantic 时声明成 float，精度就丢了。序列化时统一 str(amount)，或者 Pydantic 里用 condecimal。

总结

回到开头那个 QPS 卡在 800 的服务。换成 Tortoise + asyncpg 后，同样的硬件 QPS 上到 4000+，CPU 也跑满了——因为事件循环终于不用等线程池了。这个提升的本质，不是 ORM 换了个名字，而是数据库 IO 从“线程阻塞”变成了“协程挂起”，一个事件循环能同时挂起成百上千个等待中的查询。

几个要点回顾：

  • 异步 ORM 的“异步”取决于底层驱动，Tortoise 用 asyncpg/aiomysql/aiosqlite，是原生异步，没有线程池兜底。
  • 连接池是 loop-bound 的，跨事件循环复用会炸，测试和部署都要注意。
  • 事务靠 ContextVar 绑定连接，事务内所有操作必须 using_db(conn)，且不能并发共享连接。
  • 选型看场景：Tortoise 胜在 Django 式 API 和干净异步链路，SQLAlchemy 2.0 async 胜在复杂模型和成熟迁移，asyncpg 裸用胜在极致控制。

延伸思考：异步 ORM 的下一个战场其实是连接池的可观测性。Tortoise 目前对池的监控指标（等待队列长度、借出/归还速率、慢查询）支持很弱，生产环境经常要靠 pg_stat_activity 反推。如果你的服务规模到了一定量级，考虑在 ConnectionHandler 外面包一层埋点，或者干脆上 PgBouncer 做连接复用——把池的管理从应用层下沉到中间件层，这往往是异步 ORM 高并发场景下的最终形态。
