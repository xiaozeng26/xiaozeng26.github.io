当 ARIMA 遇上 Transformer：一份架构师的时间序列预测选型与落地手记

引言

去年我接手一个工业物联网平台的重构。平台接入了 3000 多台注塑机，每台机器每 5 秒上报一次模温、压力、保压时间等 12 个传感器指标。业务方的需求很朴素："能不能提前 30 分钟告诉我这台机器要出次品？"

听起来是个标准的时序预测问题。我当时的想法很直接：套个 ARIMA 不就行了？毕竟这是教科书里写了几十年的东西。结果第一版上线就翻车了——模温序列呈现出明显的多周期叠加（模具开合的短周期 + 环境温度变化的日周期 + 换模导致的趋势突变），ARIMA 的差分阶数怎么调都在"过差分"和"欠拟合"之间反复横跳。更致命的是，产线有 3000 条序列，用 statsmodels 逐条拟合，光参数估计就要跑两个多小时，根本满足不了模型日更的需求。

这个坑逼着我重新梳理了整个技术栈，最终落地的方案是一个"统计模型打底 + 深度模型兜底 + LLM 做异常解释"的混合架构。这篇文章就是这次选型与落地过程的复盘，我会从源码级别拆解 ARIMA 到底在算什么、深度模型（尤其是 Transformer 家族）为什么能在长序列上赢、以及 3000 条序列规模化推理时那些文档里不会写的坑。

面向的是有 3-5 年经验、真正要把模型塞进生产系统的工程师，所以我会跳过"什么是时间序列"这种科普，直接上硬菜。

核心概念：从"看后视镜开车"到"看整条路况"

先用一个生活化的类比把两类模型的心智模型立起来。

ARIMA 像是一个只看后视镜的司机。 它假设"下一时刻的值，主要由过去几个时刻的值线性组合决定，再加上一点随机扰动"。它开车的依据是后视镜里刚过去的那几百米路。这在路况平缓时非常可靠，但一旦前方有个急转弯（趋势突变、周期性事件），它只能等撞上了才反应过来。本质上它是自回归（AR）+ 差分（I）+ 移动平均（MA） 三件套：AR 用历史值回归，MA 用历史残差回归，I 用差分把非平稳序列"拍平"成平稳序列。

深度学习模型（尤其是 Transformer）像是一个能看到整条路况的导航。 它不预设"未来只依赖最近几帧"，而是通过注意力机制，让模型自己学习"预测这一时刻，应该回头去看序列里的哪些位置"。可能在预测明天早上 8 点的模温时，它自动把注意力放到了"昨天早上 8 点"和"上一个换模周期结束后的第 3 小时"上。这种长程依赖 + 多周期对齐的能力，是 ARIMA 天然缺失的。

技术上，两者的分野可以用一句话概括：

  • ARIMA 是参数化统计模型，假设序列由线性结构 + 高斯噪声生成，参数（p, d, q）通过 AIC/BIC 或自相关图确定，可解释性极强，样本效率高（几百个点就能拟合）。
  • 深度时序模型是非参数化函数逼近器，用神经网络学一个从历史窗口到未来窗口的映射，能捕捉非线性、多变量耦合、长程依赖，但需要更多数据，且推理成本高。

源码/原理深度分析

ARIMA 的内核：statsmodels 到底在算什么

很多人用 ARIMA 就是 ARIMA(data, order=(p,d,q)).fit() 一把梭，但不知道 fit 里到底发生了什么。我们扒一下 statsmodels.tsa.arima.model.ARIMA 的实现路径。

ARIMA 的核心是把模型转成状态空间形式（State Space），然后用卡尔曼滤波（Kalman Filter） 做极大似然估计。这是 statsmodels 新 API（arima.model）相比老 API（arima_model，用 Hannan-Rissanen 或 CSS 条件最小二乘）最大的升级——卡尔曼滤波能处理缺失值，且似然函数更精确。

关键在 statsmodels/tsa/statespace/_representation.pyx 里。ARIMA(p,d,q) 会被重写为：

  • 状态向量 α_t 包含 AR 项和 MA 项的历史
  • 观测方程：y_t = Z α_t + d_t + ε_t
  • 状态转移：α_{t+1} = T α_t + c_t + R η_t

其中 ε_t ~ N(0, H_t) 是观测噪声，η_t ~ N(0, Q_t) 是状态噪声。fit() 调用 _fit_mle，内部用 L-BFGS-B 优化器最大化预测误差分解（Prediction Error Decomposition） 得到的对数似然：

v_t 是 t 时刻的一步预测误差（innovation），F_t 是其方差。卡尔曼滤波每步递推 v_t 和 F_t，优化器调整 AR/MA 系数和方差参数让这个似然最大。

这就是为什么 ARIMA 慢。 每一步似然评估都要跑一遍完整的卡尔曼滤波递推（O(n) 复杂度，n 是序列长度），而 L-BFGS-B 每轮迭代要评估多次似然，参数维度随 p+q 增长。3000 条序列 × 每条 2000 个点 × 每次拟合约 0.5 秒，串行下来就是文档里那个"两小时"的来源。

理解了这层，优化方向就明确了：要么减少序列长度（下采样/聚合），要么并行化，要么换模型。我最终选了后两者结合。

深度模型的内核：PatchTST 为什么"切块"比"逐点"强

深度时序模型这几年卷得很凶。从 LSTM 到 Transformer，再到 2023 年之后的 PatchTST、iTransformer、DLinear，核心矛盾一直是：Transformer 的 O(L²) 自注意力在长序列上太贵，而且时序数据的局部性被逐点 token 化破坏得很厉害。

PatchTST（ICLR 2023）的关键洞察，用类比说就是：你读一篇文章不会一个字一个字看，而是按词组、按句子看。 时序也一样，相邻的点高度冗余，逐点做 token 既浪费算力又学不到局部模式。于是它把序列切成不重叠的 patch（比如长度 16），每个 patch 作为一个 token 送进 Transformer。

通道独立（Channel Independence） 是另一个精髓：多变量序列不做通道混合，每个通道单独走一遍 Transformer，共享权重。这相当于给每个传感器配一个"专属分析师"，避免了通道间噪声互相污染——这在工业场景里特别关键，因为模温和压力两个通道的相关性其实很弱，硬混在一起反而学乱。

PatchTST 把注意力复杂度从 O(L²) 降到 O((L/P)²)。L=512、P=16 时，计算量直接降到 1/1024。这就是它能在单卡上跑长序列预测的原因。

iTransformer（ICLR 2024）则换了个思路：把"通道"当 token，把"时间步"当特征维度。自注意力在通道之间算，学的是"哪些传感器之间有关联"。这个视角在多变量预测里非常优雅，尤其适合传感器数量不多（几十个）但序列很长的场景。

我的选型结论：不是二选一，而是分而治之。用序列画像（长度、平稳性、通道数）做路由——短且平稳的走 ARIMA 做基线（快、可解释、运维友好），长且多周期的走 PatchTST/iTransformer，异常解释交给 LLM。这个路由逻辑就是开头那张架构图里的 C{序列画像路由} 节点。

最佳实践与避坑指南

1. 别在原始尺度上评估。 时序预测的 MAPE 在接近 0 的值上会爆炸。用 MASE 或 sMAPE，或者对序列做标准化后再算指标。我见过团队因为用 MAPE 评估，把模型优化成了"专门预测大值"的偏科生。

2. 差分阶数别贪多。 ADF 检验通过就停，d 每多一阶，预测方差就放大一次。我那个注塑机案例里，d=2 时预测区间宽到毫无业务价值，最后靠"换模事件"作为外生变量（ARIMAX）才解决。

3. 深度模型的"回看窗口"要大于最长周期。 如果你的业务有日周期（24 点）和周周期（168 点），seq_len 至少得覆盖 168 个点，否则模型根本看不到完整周期。这是 PatchTST 论文里强调、但很多工程实现忽略的点。

4. 批量推理用 Ray 而非多进程。 3000 条序列的模型推理，joblib 的进程池在模型加载上会重复开销（每个进程一份模型），Ray 的 actor 模式能共享模型、复用 GPU，实测吞吐提升 3-5 倍。

5. LLM 层一定要做输出校验。 LLM 会编造"传感器编号 S-999"这种不存在的实体。用 Pydantic 做结构化输出约束，或加一层规则校验，把幻觉挡在业务系统之外。

6. 永远保留朴素基线。 用 naive（上一周期同位置的值）做兜底。任何模型在线上表现不如朴素基线时，自动降级——这是我在一次模型漂移事故后加的保险，至今救了两次。

7. 监控数据漂移，而非只监控预测误差。 预测误差是滞后的，数据分布漂移（比如换了一批原材料，传感器基线整体偏移）是前置信号。用 PSI 或 KS 检验监控输入分布，比等 MAPE 涨上去再报警早好几天。

总结

回到开头那个问题："提前 30 分钟预测次品"。最终的方案不是某个单一模型，而是一套分层架构：ARIMA 负责给 70% 的平稳序列做快速基线，PatchTST 承接 20% 的多周期复杂序列，LLM 解释层处理 10% 的异常归因。这套组合让模型日更从两小时压到 15 分钟，异常解释的工单处理效率提升了约 40%。

几个延伸思考留给你：

  • 时序基础模型（TimeGPT、Chronos、Moirai）值得关注。 它们走的是"预训练 + 零样本预测"路线，很像 LLM 之于 NLP。但目前在小样本工业场景的稳定性还没被充分验证，我持谨慎乐观态度。
  • 预测和因果要打通。 预测"模温会升高"是相关性，解释"为什么升高"需要因果图。LangGraph 那层目前是启发式归因，下一步我想接入 DoWhy 做反事实推断。
  • 别忘了工程化的脏活。 缺失值插补、时间对齐、时区处理、夏令时——这些占了我 60% 的开发时间，却很少出现在论文里。模型再先进，脏数据喂进去也是垃圾出。

技术选型没有银弹，只有权衡。把每类模型的"能力边界"和"成本边界"摸清楚，再用架构把它们组合起来，这才是架构师该干的活。
