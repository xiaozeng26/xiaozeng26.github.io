别再只盯着 LangChain 了：从执行模型源码看 LangChain/LangGraph、LlamaIndex、CrewAI、AutoGen 的真实分水岭

引言

先说一个我去年踩过的坑。

团队要做一个"合同审阅 Agent"：解析 PDF → 抽取条款 → 对照法规库检索 → 逐条给出风险评级 → 生成审阅报告。第一版我们用 LangChain 的 AgentExecutor + 一堆 Tool 拼出来，Demo 跑得飞快，老板很满意。上线两周后问题来了：

  1. 审阅到第 3 条时模型突然"忘记"前面已经查过哪条法规，重复检索，token 烧得飞快；
  2. 某次法规库 API 超时，整个流程直接抛出 MaxIterationsExceeded，前面 20 分钟的解析全白干；
  3. 我们想让"抽取 Agent"和"评级 Agent"并行跑，发现 AgentExecutor 的 ReAct 循环是串行文本驱动的，根本插不进去。

痛定思痛，我把四个框架的源码翻了一遍，最后用 LangGraph 重写，问题 2、3 迎刃而解。那次之后我形成一个观点：选 Agent 框架，别看它有多少 Star、多少 Tool 集成，要看它的"执行模型"——也就是"控制流由谁来编排"。这个差异，比任何 API 表面差异都致命。

这篇文章就从这个角度切入，带你从源码层面看清四个框架的分水岭。

核心概念：控制流到底归谁管？

先上一个生活化类比。

想象你开一家餐厅，厨房里有一群厨师（LLM + Tool）：

  • LangChain 的 AgentExecutor：像一个"传菜员"，他拿着顾客的原始需求，跑到后厨问大厨"下一步干啥？"，大厨说"切菜"，传菜员就去切菜窗口；切完再跑回来问"下一步？"，大厨说"下锅"…… 每一步都要回到大厨那里问一次，而且传菜员脑子里只有"大厨刚说的那句话"，没有全局菜单。这就是 ReAct 循环的本质：文本驱动的单步决策。
  • LangGraph：像一张"厨房流程图"贴在墙上，每个工位（Node）负责一道工序，工序之间用箭头（Edge）连起来，还有"如果汤咸了就回锅"这种条件分支（Conditional Edge）。控制流被显式地画出来了，状态放在中央备餐台（State）上，谁都能看。
  • LlamaIndex：像一本"索引目录 + 标准菜谱"。它最擅长的是"根据关键词快速翻到对应菜谱页"（检索），然后按菜谱步骤做。它的 Workflow 是事件驱动的，比 LangGraph 更"松耦合"，适合以"数据/文档"为中心的流程。
  • CrewAI：像一个"餐厅管理团队"，有店长（Manager）、服务员（Role）、后厨（Task），店长负责分派任务、检查成果。它把"角色 + 任务 + 协作"作为一等公民，本质是"多 Agent 编排层"。
  • AutoGen：像一个"开放式厨房"，几个厨师围着一口锅，谁有想法谁说话（GroupChat），或者两两结对（Two-Agent）。它把"对话"作为协作原语，控制流是"涌现"出来的，而不是预先画好的。

用一张表先钉住四者的执行模型差异：

框架 控制流归属 状态管理 协作原语 典型心智模型
LangChain (AgentExecutor) 框架内部循环 隐式（在 scratchpad 文本里） Tool 调用 单 Agent + 工具
LangGraph 开发者显式编排 显式 State（TypedDict/Pydantic） 图节点/边 状态机
LlamaIndex (Workflow) 事件触发 Context（可持久化） Event 事件驱动流水线
CrewAI Manager/流程 Task 上下文 Role + Task 组织架构
AutoGen 对话协议 消息历史 消息/GroupChat 多智能体对话

下面进入源码深水区。

源码/原理深度分析

1. LangChain AgentExecutor：为什么它天生"健忘"且"难并行"

我们直接看 langchain 包里 AgentExecutor 的核心循环（简化自 libs/langchain/langchain/agents/agent.py）：

关键点有三个，全是从这段代码里能读出来的：

第一，"状态"其实就是 intermediate_steps 这个 list。 而它被 _agent.plan 序列化成一段文本（Thought/Action/Observation 的格式）塞进 prompt。这意味着：所谓"记忆"，本质是把历史对话拼成字符串。上下文窗口一满，早期的 Observation 就被截断——这就是我遇到的"忘记查过哪条法规"的根因。它不是 bug，是设计使然。

第二，循环是串行且"黑盒"的。 for i in range(max_iterations) 里每一步都强依赖上一步的 observation。你想让"抽取"和"检索"并行？在这个循环里没有位置。max_iterations 耗尽直接抛异常，中间产物不落盘，这就是我"20 分钟白干"的原因。

第三，plan 的决策权完全在 LLM 手里。 框架不知道"下一步该干什么"，它只知道"问 LLM"。这种文本驱动的架构优点是灵活（LLM 想怎么走怎么走），缺点是不可预测、不可测试、不可恢复。

一句话总结：AgentExecutor 是一个"while 循环 + LLM 做 if-else"的朴素实现。它能跑通 Demo，但撑不起生产级的可观测性和可恢复性。

2. LangGraph：把"隐式循环"变成"显式状态机"

LangGraph 的核心抽象就三个：StateGraph、Node、Edge。看它的编译和执行逻辑（简化自 langgraph/graph/state.py 和 pregel 执行器）：

执行器用的是 Pregel/BSP（Bulk Synchronous Parallel）模型：每一"超步"里，所有活跃节点并行执行，产出对 State 的增量更新，然后用 reducer 合并。这是它和 AgentExecutor 最本质的区别——状态是显式的、可合并的、可持久化的。

这个 reducer 机制是精髓。你在一个超步里并行跑"抽取条款""检索法规""风控校验"三个节点，它们各自只返回自己那部分增量，执行器负责合并。并发天然被支持，因为节点之间通过 State 解耦，而不是通过 observation 文本串行传递。

再看它的 checkpointer（langgraph/checkpoint/）：每个超步结束，State 被序列化落盘（SQLite/Postgres/内存）。这意味着流程可以断点续跑——我那个"API 超时"的痛点，在 LangGraph 里只需在失败节点加重试策略，或从上一个 checkpoint 恢复，前面的解析结果都还在。这就是"显式状态"带来的工程红利。

用图直观对比两种执行模型：

3. LlamaIndex Workflow：事件驱动的"松耦合流水线"

LlamaIndex 早期以 RAG 闻名，但它的 Workflow（llama_index/core/workflow/）是一个被低估的编排引擎。核心是 @step 装饰器 + Event：

和 LangGraph 的差异在于：LangGraph 的边是显式画出来的（add_edge），而 LlamaIndex 的 step 之间是通过 Event 类型隐式连接的——step A 产出 EventX，step B 声明 accept EventX，两者就自动接上了。这是发布/订阅模型。

优点：解耦彻底，加一个 step 不用改图；step 可以并发（多个 step 订阅同一 Event）。缺点：控制流不直观，调试时你得"顺着 Event 类型"去追，图不在你脑子里。所以它更适合以数据处理为中心的流水线（文档解析 → 分块 → 嵌入 → 检索 → 生成），而不是复杂的多轮决策。

4. CrewAI 与 AutoGen：多 Agent 协作的两种哲学

CrewAI（crewai/crew.py）的核心是 Crew + Agent + Task。它有两种 Process：sequential（按 Task 顺序）和 hierarchical（有个 Manager Agent 分派）。看它的 sequential 执行：

它的价值在抽象层次高：你写的是"角色、目标、任务"，而不是"节点、边"。对业务同学友好。但代价是控制流灵活性受限——你要做复杂分支、循环、并行，就得下沉到它的底层或换框架。它本质是"在 LangChain 等底座上加了一层组织编排 DSL"。

AutoGen（autogen/agentchat/）的核心是 ConversableAgent + GroupChat。它的协作原语是消息：

它的控制流是涌现式的：谁发言由 selector 决定（可以是 LLM 投票、可以是轮询、可以是自定义规则）。优点是极其灵活，能模拟"头脑风暴""辩论""结对编程"；缺点是不可预测、容易跑飞、成本不可控（多 Agent 互相聊，token 爆炸）。生产上必须配 max_round 和严格的终止条件。

选型建议（我的经验法则）：

  • 流程有明确分支、循环、需要断点续跑 → LangGraph；
  • 流程是文档/数据流水线、要频繁加处理环节 → LlamaIndex Workflow；
  • 业务方参与设计、强调角色分工、流程相对线性 → CrewAI；
  • 需要开放式多 Agent 讨论/辩论/结对、能接受一定不确定性 → AutoGen；
  • 只是做个单 Agent 调几个 Tool 的 Demo → LangChain AgentExecutor 够用，但别上生产。

最佳实践与避坑指南

  1. 状态别塞进 prompt。 AgentExecutor 的 intermediate_steps 序列化是反模式。用 LangGraph 的显式 State，或至少自己维护结构化记忆，别指望 LLM 记住 20 轮前的 Observation。
  1. 给每个 Agent 设"预算"。 AutoGen 的 max_round、LangGraph 的 recursion_limit、CrewAI 的 max_iter，不设就是给账单开盲盒。我见过 AutoGen 两个 Agent 互相客套聊了 40 轮烧掉 3 美元的。
  1. 节点/step 要幂等。 断点恢复意味着节点可能被重跑，写库、发消息这类副作用必须幂等（用 upsert 而非 insert，用幂等 key）。
  1. 并行节点别共享可变对象。 LangGraph 的 reducer 只合并"返回值增量"，如果你在节点里 state["findings"].append(...) 原地改，会踩并发坑。永远返回新对象。
  1. 可观测性从第一天就上。 用 LangSmith / Langfuse 之类追踪每个节点的输入输出。多 Agent 系统出问题时，"谁在哪一步说了什么"是唯一救命稻草。
  1. 别为了"多 Agent"而多 Agent。 很多需求单 Agent + 好工具就能解决。多 Agent 的通信开销和不确定性是指数级的，CrewAI/AutoGen 不是银弹。
  1. MCP 作为工具层解耦。 2025 年后 MCP（Model Context Protocol）逐渐成为工具接入的事实标准。把 Tool 实现成 MCP Server，四个框架都能接，避免工具层和编排层绑死——这是我今年最推荐的架构习惯。

总结

回到开头那个坑。四个框架的分水岭，不在 API 多花哨，而在"控制流归谁管"：

  • AgentExecutor 把控制流交给 LLM 的文本决策，简单但不可控、不可恢复；
  • LangGraph 把控制流显式画成状态机，用 reducer 支持并行、用 checkpointer 支持恢复，是复杂生产流程的首选；
  • LlamaIndex Workflow 用事件解耦，适合数据流水线；
  • CrewAI 和 AutoGen 把协作抽象成角色/任务和对话，前者可预测、后者更灵活，都需强约束才能上生产。

一个延伸思考：这四种执行模型其实对应了分布式系统里四种经典范式——命令式循环、状态机、发布订阅、Actor 对话。理解了这层映射，你换任何新框架都能快速定位它的"性格"。下次再有人问你"选哪个 Agent 框架"，你可以反问他一句："你的控制流，是想画出来，还是想聊出来？"
