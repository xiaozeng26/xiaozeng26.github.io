别再傻傻分不清：从源码层面拆解 OAuth2、OIDC 与 JWT 的边界，以及那 7 个让无数团队翻车的认证陷阱

别再傻傻分不清：从源码层面拆解 OAuth2、OIDC 与 JWT 的边界，以及那 7 个让无数团队翻车的认证陷阱

引言

先讲一个我亲身经历的生产事故。

2023 年，我接手一个 SaaS 项目的安全审计。这个项目用了 OAuth2 登录、JWT 做会话、还接了 OIDC 做 SSO。架构图看起来非常"标准"，团队也自认为很懂。结果我花了两个小时，就找出了三个越权漏洞：

第一个，他们的 JWT 里塞了 role: "user"，但后端只校验签名，不校验 aud 和 iss——攻击者拿另一个业务线的 token 就能横向越权。第二个，OIDC 的 id_token 被当成了 access_token 拿去调 API，因为两者长得太像,都是 JWT。第三个，刷新令牌（refresh token）没有轮换（rotation），泄露一次就能永久续命。

这三个问题的根源是同一个：团队没有搞清楚 OAuth2、OIDC、JWT 这三者到底各管什么事。它们经常被混为一谈，但它们其实是三个不同层次的东西——一个是授权框架，一个是身份认证层，一个是令牌格式。就像"餐厅管理流程"、"会员身份核验"、"会员卡"之间的关系，你可以拿会员卡（JWT）去核验身份（OIDC），但会员卡本身既不是流程也不是核验规则。

这篇文章，我会从源码层面拆开这三者的实现，用生活类比讲清楚它们的边界，然后给出三个可以直接跑的生产级代码示例，最后聊聊那些"看起来能用、实际上致命"的坑。

核心概念：用"游乐园"类比理清三者关系

生活类比

想象一个大型游乐园：

  • OAuth2 是游乐园的授权体系。你（用户）来到门口，想要让"代泊车服务"（第三方应用）帮你把车停好，但你不想把车钥匙直接给它，也不想让它能进你的酒店房间。于是游乐园发给你一张有限权限的临时手环（scope 受限的 access token），代泊车服务拿着手环只能做"泊车"这一件事。这就是 OAuth2 的本质：委托授权，它回答的是"这个应用能代表我做什么"。
  • OIDC 是在 OAuth2 之上加的身份核验层。你进园时需要证明"我就是这张年卡的持有人"。游乐园的核验窗口会给你一张带照片的身份卡（id_token），上面写着"张三，年卡会员，有效期到年底"。这就是 OIDC：它回答的是"你是谁"。它复用 OAuth2 的流程，但额外定义了身份信息的标准格式。
  • JWT 是卡片的物理材质。无论是临时手环还是身份卡，都可以用同一种"防伪塑料"制作——这就是 JWT。它是一种令牌的编码格式，本身不规定用途。手环可以用 JWT 做，身份卡也可以用 JWT 做，但你不能因为两张卡材质一样，就认为它们权限一样。

技术定义

概念 本质 回答的问题 规范
OAuth2 授权框架（Authorization Framework） 应用能代表用户做什么？ RFC 6749
OIDC 身份认证层（Authentication Layer） 用户是谁？ OpenID Connect Core 1.0
JWT 令牌格式（Token Format） 如何安全地编码声明？ RFC 7519

关键洞察：OAuth2 不是认证协议。这是 RFC 6749 里明确写的（原文：*"OAuth 2.0 is not an authentication protocol"*）。很多团队把"用 OAuth2 登录"当成认证，这本身就是概念混淆的起点。OIDC 才是为此而生的补丁。

源码/原理深度分析

JWT 的结构与签名机制

JWT 由三段 Base64URL 编码拼接而成：header.payload.signature。

这里有一个绝大多数人忽略的细节：JWT 的 payload 是明文可读的，只是 Base64URL 编码，不是加密。你在 payload 里塞的任何东西，任何人拿到 token 都能解出来。所以绝不能在 JWT 里放敏感数据（密码、身份证号、密钥）。

这些字段不是随便起的，每一个都有校验语义，少校验一个就是一个漏洞：

  • iss（Issuer）：签发者。必须和你配置的 IdP 完全匹配，否则攻击者可以伪造一个自己的 IdP 发 token。
  • sub（Subject）：用户唯一标识。同一用户在同一个 iss 下 sub 稳定。
  • aud（Audience）：受众。必须包含你的 client_id。不校验 aud，就是开头那个事故的第一个漏洞。
  • exp / iat：过期时间、签发时间。必须校验 exp。
  • nonce：防重放。登录时生成，回调时校验，防止 token 被截获重放。
  • at_hash：access_token 的哈希。用于绑定 id_token 和 access_token，防止两者被"调包"。

OAuth2 授权码流程的时序

sequenceDiagram participant U as 用户浏览器 participant C as 客户端(第三方应用) participant AS as 授权服务器(IdP) participant RS as 资源服务器(API) U->>C: 点击"用某账号登录" C->>U: 重定向到 AS /authorize?client_id&scope&state&nonce U->>AS: 用户登录并授权 AS->>U: 重定向回 C 的 callback?code=xxx&state=yyy U->>C: 携带 code 回调 C->>AS: POST /token (code + client_secret + PKCE verifier) AS->>C: 返回 access_token + id_token + refresh_token C->>RS: 携带 access_token 调用 API RS->>RS: 校验 token（JWT 验签或 introspection） RS->>C: 返回资源

这个流程里有三个安全锚点：state（防 CSRF）、PKCE（防授权码拦截）、code 只能用一次（防重放）。任何一个缺失，都是攻击面。

一个常见的架构误区

很多人以为 JWT 是 OAuth2 的一部分。不是。OAuth2 规范里 access_token 是"不透明字符串（opaque string）"，格式由实现决定。JWT 只是其中一种可选的令牌格式。你可以用随机字符串 + 服务端存储（introspection）的方式实现 OAuth2，这也是很多金融级系统的选择。

上图说明：JWT 和 OIDC 的 id_token 是"强绑定"，但 JWT 和 OAuth2 的 access_token 是"弱绑定"。搞混这一点，就会写出把 id_token 当 access_token 用的代码——这正是引言里第二个漏洞。

方案对比：三种主流认证方案怎么选

方案 令牌形态 状态管理 适用场景 致命弱点
Session + Cookie 随机 sessionId 服务端有状态 单体、同域 Web 应用 跨域/多端难扩展；需共享 session 存储
OAuth2 + 不透明 token 随机字符串 + introspection 授权服务器有状态 金融、高安全、需要即时吊销 每次请求都要 introspection，性能开销大
OAuth2 + JWT 自包含 JWT 无状态（可加黑名单） 微服务、跨域、高并发 无法即时吊销；令牌泄露窗口大

我的观点：不要迷信"无状态 JWT 一定好"。JWT 的最大卖点是省掉一次查库，代价是吊销困难。如果你的业务需要"立即踢人下线"（比如金融、后台管理），用 introspection 或短 TTL + refresh 轮换更稳妥。JWT 适合"读多写少、容忍短暂延迟吊销"的场景。

再补一个对比：IDaaS 托管 vs 自研。Auth0、Keycloak、AWS Cognito 这类托管方案能帮你把 OIDC 的各种边界情况处理掉，但自研能完全掌控数据和流程。我的经验是：认证这种"错了就全盘皆输"的模块，能托管就托管，把精力留给业务。自研的团队，往往在 nonce、PKCE、轮换这些细节上翻车。

最佳实践与避坑指南

坑 1：alg=none 攻击

JWT header 里的 alg 是攻击者可控的。如果验证方不限制算法，攻击者把 alg 改成 none、删掉签名，某些库会"验证通过"。对策：永远显式指定允许的算法白名单，如示例 1 的第 2 步。

坑 2：算法混淆（RS256 → HS256）

如果服务端用公钥验 RS256，攻击者把 alg 改成 HS256，并用公钥当 HMAC 密钥重新签名，某些实现会误判通过。对策：验签时锁定算法，且公钥绝不用于 HMAC。

坑 3：不校验 aud / iss

这是开头事故的元凶。多租户系统里，A 租户的 token 能访问 B 租户的 API。对策：把 aud、iss 校验写进统一的中间件，强制所有端点走。

坑 4：id_token 当 access_token 用

两者都是 JWT，长得像，但语义完全不同。id_token 是给客户端验证用户身份的，access_token 是给资源服务器授权访问的。对策：在类型系统上区分（不同 struct/class），资源服务器只接受 access_token。

坑 5：refresh token 不轮换

泄露一次，永久续命。对策：每次刷新都换新 refresh，旧的一次性作废，并做复用检测（示例 3）。

坑 6：JWT 里塞敏感数据

payload 明文可读。对策：只放 sub、scope、exp 这类非敏感声明。

坑 7：忽略 clock skew

分布式系统里各机器时间有偏差，exp 校验过于严格会误杀。对策：允许 30~60 秒的时钟偏移（leeway），但不要超过 5 分钟。

最佳实践清单

  1. 认证用 OIDC，授权用 OAuth2，令牌格式按场景选 JWT 或不透明串——三者各司其职。
  2. 所有 token 校验集中到一个中间件，杜绝"某个端点忘了校验"。
  3. access_token 短 TTL（5~15 分钟）+ refresh token 轮换，把泄露窗口压到最小。
  4. 公共客户端必须用 PKCE，机密客户端也要用（纵深防御）。
  5. state、nonce、code 一次性，三个防重放锚点一个不能少。
  6. JWKS 缓存 + 定期刷新，避免每次验签都请求 IdP。
  7. 监控异常刷新行为，复用检测触发时告警，这是入侵的强信号。

总结

回到开头那个事故。那三个漏洞的本质，是把三个不同层次的东西混为一谈：

  • OAuth2 是授权框架，管"能做什么"，它本身不做认证；
  • OIDC 是认证层，管"你是谁"，它的核心是对 id_token 一堆字段的严格校验；
  • JWT 是令牌格式，管"怎么编码声明"，它既不等于授权也不等于认证。

理解了这层边界，很多"最佳实践"就不再是需要背的教条，而是自然的推论：既然 OIDC 靠校验字段保证安全，那 aud、iss、nonce 一个都不能少；既然 JWT 是无状态自包含的，那吊销困难就是它的固有代价，短 TTL + 轮换是必然选择。

最后留一个延伸思考：零信任（Zero Trust） 的浪潮下，"一次认证、长期有效"的模型正在被"持续验证"取代。JWT 的"自包含"特性在零信任里其实是双刃剑——它让你省了查库，却让你无法感知"这个用户 5 分钟前刚被降权"。未来，短生命周期令牌 + 持续风险评估（比如结合设备指纹、行为分析）会成为主流。到那时，JWT 可能更多扮演"短期凭证"的角色，而"身份真相"会重新回到有状态的授权服务器手里。

技术没有银弹，只有对边界的清醒认知。搞清楚 OAuth2、OIDC、JWT 各管什么，比记住任何一条最佳实践都重要。
