别再堆组件了：从 Nacos、Sentinel、Seata 的源码看微服务治理的“三层边界”

引言

先说一个我最近接手项目时看到的真实场景。

一个电商系统，拆了 20 多个微服务，Spring Cloud Alibaba 全家桶一应俱全：Nacos 做注册中心和配置中心，Sentinel 做限流熔断，Seata 做分布式事务。配置文件加起来上千行，看起来非常“云原生”。然后压测一开始，问题全来了：

  • 商品服务挂了，订单服务调用它超时 30 秒，线程池被拖死，接着整条链路雪崩——Sentinel 明明配了熔断，为什么没生效？
  • 用户下单扣了库存，但支付服务抛异常回滚了，库存却没回滚——Seata 的 @GlobalTransactional 明明加了，为什么事务没回滚？
  • Nacos 配置改了一个限流阈值，过了 10 分钟才生效——说好的动态配置呢？

排查下来，三个问题的根因惊人地一致：大家都在“用”组件，但没人搞清楚每个组件到底治理的是哪一层的边界。Nacos 管的是“服务发现与配置”的边界，Sentinel 管的是“流量与调用”的边界，Seata 管的是“数据一致性”的边界。三条边界职责不同、失效模式不同、生效时机也不同。把它们当成三个可以随便堆砌的 SDK，出事是必然的。

这篇文章，我想从源码层面把这三层边界彻底讲透，并且给出可直接落地的工程实践。读完你应该能回答：为什么你的 Sentinel 熔断没生效、为什么你的 Seata 事务不回滚、为什么你的 Nacos 配置不刷新。

核心概念：三层边界，三个“后厨角色”

先用一个餐厅的类比把三者的定位说清楚。

把整个微服务系统想象成一家大型连锁餐厅：

  • Nacos 是“前厅调度 + 菜谱公告栏”。它知道今天哪个厨师在岗（服务注册）、客人该去哪个窗口点菜（服务发现），同时墙上贴着所有菜谱（配置），菜谱改了要通知到每个厨房（配置刷新）。它管的是“谁在哪、规则是什么”。
  • Sentinel 是“门口的取号限流员 + 后厨的熔断开关”。客流太大就限流（FlowRule），某个灶台老是炒糊（异常比例高）就暂时关掉这个灶台，别让客人一直等（熔断降级）。它管的是“流量怎么进、调用失败了怎么办”。
  • Seata 是“跨多个档口的订单一致性管理员”。一笔订单要同时扣库存档口、扣款档口、生成物流单档口，任何一个档口失败，其他档口必须撤销。它管的是“多个数据源之间怎么保证原子性”。

用一张图展示这三层边界在一个请求链路中的位置：

graph TD Client[客户端请求] --> Gateway[网关] Gateway -->|1. 服务发现: 拿到实例列表| Nacos[(Nacos 注册/配置中心)] Gateway -->|2. 流量控制/熔断| Sentinel[Sentinel 流量治理] Sentinel --> OrderService[订单服务] OrderService -->|3. 开启全局事务| Seata[Seata TC 事务协调器] Seata --> OrderService OrderService -->|Feign 调用 + 服务发现| Nacos OrderService -->|调用| StockService[库存服务] OrderService -->|调用| PayService[支付服务] StockService -->|分支事务注册| Seata PayService -->|分支事务注册| Seata OrderService -.配置动态刷新.-> Nacos style Nacos fill:#e1f5ff style Sentinel fill:#fff4e1 style Seata fill:#ffe1e1

关键认知：这三层是正交的。Nacos 挂了，服务调不通，Sentinel 和 Seata 都无从谈起；Sentinel 配错了，流量打崩服务，Seata 事务也没机会提交；Seata 的事务边界没划对，数据就脏了。它们是串联在请求生命周期上的三道闸门，而不是三个并列的插件。

源码/原理深度分析

一、Nacos：配置动态刷新的“推拉结合”真相

很多人以为 Nacos 配置刷新是纯推送。实际上 Nacos 客户端采用的是“长轮询（long polling）+ 本地缓存”的推拉结合模型。这是理解“为什么配置 10 分钟才生效”的钥匙。

看 nacos-client 的核心类 ClientWorker，它内部维护了一个 executor 线程池，对每个监听的 dataId 发起长轮询请求：

服务端的 LongPollingService 收到请求后，不会立即返回，而是把请求挂起（默认 30 秒），期间如果有配置变更就立即唤醒返回；30 秒到了没变更就返回空，客户端再发起下一轮。这就是长轮询。

坑点一：如果你在 bootstrap.yml 里配置了 nacos.config.refresh-enabled=false，或者用了 @Value 而没加 @RefreshScope，配置压根不会注入到 Bean。@Value 只在 Bean 初始化时求值一次，刷新时 Nacos 虽然更新了 Environment，但老 Bean 里的字段还是旧值。

坑点二：@RefreshScope 的 Bean 在刷新时会被销毁重建（它是个代理，刷新时清空 target 缓存）。如果你的 Bean 持有连接池、线程池这类有状态资源，重建会导致泄漏。正确做法是把配置项抽到一个 @ConfigurationProperties 的 POJO，依赖它的 Bean 通过 getter 读，而不是把配置散落在业务 Bean 的字段里。

二、Sentinel：熔断不生效，90% 是资源定义和规则下发的锅

Sentinel 的核心模型是 资源（Resource）+ 规则（Rule）+ 槽链（Slot Chain）。每次 SphU.entry("resourceName") 都会走一遍责任链：

graph LR A[entry] --> B[NodeSelectorSlot] B --> C[ClusterBuilderSlot] C --> D[StatisticSlot] D --> E[FlowSlot 限流] E --> F[DegradeSlot 熔断] F --> G[SystemSlot 系统保护] G --> H[业务逻辑] D -.统计.-> Stat[滑动窗口统计] E -.读规则.-> RuleMgr[FlowRuleManager] F -.读规则.-> DegRuleMgr[DegradeRuleManager]

为什么你的熔断没生效？ 源码层面有三个高频原因：

原因 1：资源名对不上。 DegradeRuleManager 是按 resource 字符串精确匹配规则的。如果你用 @SentinelResource("order") 但规则里写的是 "orderService"，永远匹配不上。更隐蔽的是 Feign 场景：默认 Feign 资源名是 GET:http://stock-service/stock/deduct 这种格式，你在控制台按 "stock/deduct" 配规则当然无效。正确姿势是配置 feign.sentinel.enabled=true 并通过 UrlCleaner 或自定义 RequestOriginParser 统一资源名。

原因 2：熔断器的“半开”状态被误读。 看 DegradeSlot 依赖的 CircuitBreaker 状态机（以慢调用比例熔断为例）：

关键：熔断打开后，只有极少数探测请求能进入半开状态，如果探测请求成功才闭合。很多人压测时看到“熔断打开了但流量还在打业务”，是因为探测请求恰好成功，状态又回到 CLOSED。这不是 bug，是设计。你需要关注的是 minRequestAmount（最小请求数）和 statIntervalMs（统计窗口）是否合理——如果窗口内请求数达不到 minRequestAmount，熔断器根本不会被触发统计。

原因 3：规则下发的是“内存规则”，重启即丢。 直接调 FlowRuleManager.loadRules() 只改本地内存。生产必须接 NacosDataSource 做持久化：

三、Seata：AT 模式的两阶段，以及“为什么没回滚”

Seata AT 模式的核心是全局锁 + undo_log 反向补偿。理解它必须看懂 DataSourceProxy 如何拦截 SQL 并生成前后镜像。

两阶段流程：

  1. 一阶段：各分支服务执行业务 SQL，同时写 undo_log，然后向 TC（Seata Server）注册分支事务。此时本地事务已提交（这是 AT 与 XA 的最大区别），但全局锁被持有。
  2. 二阶段：TC 通知全局提交 → 异步删除 undo_log；或全局回滚 → 各分支根据 undo_log 生成反向 SQL 补偿。

为什么你的 @GlobalTransactional 没回滚？ 高频原因：

  • 异常被吞了：@GlobalTransactional 默认只对 RuntimeException 和 Error 回滚。你 catch (Exception e) { log.error(...); } 没重新抛出，TC 收不到失败信号，全局提交。
  • 跨了非 Seata 代理的数据源：只有被 DataSourceProxy 包装的数据源才受管。你手动 new JdbcTemplate(rawDataSource) 或用了没配置代理的 MyBatis-Plus 多数据源，那条 SQL 不在事务里。
  • Feign 调用没传 XID：分支事务靠 RootContext 里的 XID 关联。异步线程、线程池、@Async 会丢失 RootContext，必须手动 RootContext.bind(xid) 传递。

方案对比

三个组件在业界都有替代方案，理解差异才能选对：

能力层 本文方案 主流替代 差异与适用场景
注册/配置 Nacos Eureka + Config、Consul、Apollo Nacos 注册配置二合一、AP 模型、长轮询；Apollo 配置能力更强但注册需另配；Consul 强一致 CP，适合对一致性敏感但吞吐略低
流量治理 Sentinel Hystrix（停更）、Resilience4j Sentinel 有控制台、规则动态下发、QPS/线程数双维度；Resilience4j 轻量、函数式、无中心控制台，适合 Serverless/函数场景
分布式事务 Seata AT XA、TCC、Saga、本地消息表 AT 对业务零侵入但有全局锁、性能中等；TCC 性能最好但要写三个方法；Saga 适合长流程但无隔离性；本地消息表最简单但要自己做幂等

选型建议：

  • 初创/中小规模：Nacos + Sentinel + Seata AT，全家桶开箱即用，成本最低。
  • 高并发核心交易：Seata AT 的全局锁在热点行会成瓶颈，考虑 TCC 或“本地消息表 + 最终一致”。
  • 已有 Spring Cloud Netflix 存量：Hystrix 已停更，逐步迁移到 Sentinel 或 Resilience4j，别为了迁移而迁移。

最佳实践与避坑指南

Nacos：

  1. 配置类统一用 @ConfigurationProperties，别用 @Value + @RefreshScope 组合，后者会销毁重建 Bean。
  2. 生产开启 Nacos 鉴权，配置 namespace 隔离环境，group 隔离业务线。
  3. 监听配置变更时，注意 Listener 回调里不要做重操作，它在长轮询线程里执行，会阻塞其他配置刷新。

Sentinel：

  1. 资源名统一规范，Feign 场景用 UrlCleaner 归一化，否则规则永远对不上。
  2. 规则必须持久化到 Nacos，纯内存规则重启即丢。
  3. blockHandler 和 fallback 别混用逻辑：前者是“被限流”，后者是“业务异常”，语义不同。
  4. 熔断的 minRequestAmount 别设太大，否则低流量下永远不触发统计。

Seata：

  1. @GlobalTransactional 的 rollbackFor 显式写 Exception.class，别赌默认。
  2. 异步/线程池必须手动 RootContext.bind/unbind，这是最高频的“事务丢失”根因。
  3. undo_log 表要建在每个业务库，且定期清理，否则表会膨胀。
  4. 热点行更新（如秒杀库存）慎用 AT，全局锁会串行化，考虑 TCC 或分段扣减。

通用：

  1. 三层边界要分别压测、分别观测。Nacos 看注册心跳和配置推送延迟，Sentinel 看 block 和 fallback 指标，Seata 看 TC 的全局事务数和分支回滚率。
  2. 别在网关层同时堆 Sentinel 和 Seata——网关做流量治理，事务边界应该下沉到业务编排层。

总结

回到开头那三个问题，现在应该能一句话回答了：

  • Sentinel 熔断没生效：资源名对不上 + 规则没持久化 + 没理解半开探测机制。
  • Seata 没回滚：异常被吞 + 数据源没被代理 + 异步丢了 XID。
  • Nacos 配置不刷新：@Value 没 @RefreshScope，或 refresh-enabled 被关。

更深一层的认知是：微服务治理不是“把组件堆上去”，而是“把每层边界的职责和失效模式想清楚”。Nacos 治理的是“位置与规则”的边界，Sentinel 治理的是“流量与调用”的边界，Seata 治理的是“数据一致性”的边界。三条边界正交、串联、各有各的生效时机。把源码里那几个关键类（ClientWorker、DegradeSlot、UpdateExecutor）读一遍，比看十篇配置教程有用。

延伸思考：当服务规模再上一个量级，这三层边界会开始“打架”——Nacos 的推送风暴、Sentinel 的规则一致性、Seata 的全局锁性能，都会成为新的瓶颈。那时你要考虑的就不是“怎么配”，而是“要不要下沉到 Service Mesh（Istio + Envoy 做流量，Saga 做长事务）”。但在那之前，先把这三层边界吃透，你才有资格谈架构演进。
