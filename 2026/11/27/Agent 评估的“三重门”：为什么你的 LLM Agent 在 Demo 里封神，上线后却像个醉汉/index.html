Agent 评估的“三重门”：为什么你的 LLM Agent 在 Demo 里封神，上线后却像个醉汉

引言

先说一个真实场景。

去年我参与一个客服 Agent 的落地项目。Demo 阶段，产品经理在会议室里演示：用户问“我上个月的订单为什么还没发货”，Agent 调用了订单查询 API、物流 API，还用自然语言解释了延迟原因，最后主动提出补偿方案。全场鼓掌。

三周后上线，监控面板上的数字开始变得难看：

  • 10% 的请求里，Agent 把两个用户的订单搞混了（上下文污染）；
  • 8% 的请求里，Agent 在工具调用失败后开始“编造”物流状态（幻觉）；
  • 还有一类最隐蔽：Agent 回答完全正确，但多花了 4 次工具调用、消耗了 3 倍 token——用户满意，财务不满意。

问题出在哪？我们从来没有系统性地“评估”过它。我们只做过“测试”——跑几十条用例，人工看一眼输出像不像话。这跟用肉眼看体温计判断发动机故障没有本质区别。

Agent 的可靠性不是“回答得像不像”，而是一个多维度的工程指标。 这篇文章我想讲清楚：一个生产级 Agent 的评估体系应该长什么样，为什么业界主流框架（LangGraph、AutoGen、MCP 生态）在评估上各有短板，以及如何用源码级的视角去构建你自己的评估闭环。

核心概念：Agent 评估到底在评估什么

生活类比：米其林评审 vs 食客打分

普通 LLM 评估像“食客打分”：菜好不好吃，尝一口，给个星星。简单直接，但只能反映最终输出。

Agent 评估更像“米其林评审”：评审员不仅尝菜，还要看后厨动线是否合理（工具调用路径）、食材是否新鲜（上下文质量）、出餐时间是否稳定（延迟与成本）、以及换一个评审员来吃结果是否一致（可复现性）。

一个 Agent 的可靠性 = 输出正确性 × 过程合理性 × 资源经济性 × 行为稳定性。

四个维度缺一不可。只测第一个，你得到的是一个“偶尔正确但不可控”的系统。

AutoGen 的多 Agent 对话模式（GroupChat）评估难度更高。看它的消息路由逻辑（简化自 autogen/agentchat/groupchat.py）：

这里的评估难点在于：多 Agent 的对话轨迹是涌现的，没有唯一“正确路径”。A 先问 B 还是 B 先问 A，可能都合理。所以你不能用“轨迹匹配”来评估，只能用约束满足：

  • 是否在 N 轮内收敛（没有无限乒乓）？
  • 是否每个 Agent 都只做了职责内的事（没有越界）？
  • 最终结论是否是某个 Agent 的“确认输出”而非“最后一句话”？

AutoGen 本身不提供这些评估器，你需要自己写。这是多 Agent 评估比单 Agent 评估难一个量级的根本原因。

选型建议：

  • Demo 阶段：LangSmith 够用，快速拿到终点指标。
  • 上线前：必须上轨迹评估 + 稳定性评估，否则你无法解释“为什么昨天好好的今天挂了”。
  • 多 Agent 系统：放弃“轨迹匹配”，改用“约束满足”评估（收敛性、职责边界、最终确认）。
  • 成本敏感场景：把 token 数和工具调用次数作为一等公民指标，和正确性一起看。

最佳实践与避坑指南

1. 评估数据集要“三元组化”，不是“问答对化”

传统数据集是 (question, answer)。Agent 评估数据集应该是 (question, expected_trajectory, expected_answer)。没有期望轨迹，你只能评终点；有了期望轨迹，你才能定位失败点。

2. 每个用例独立 thread_id，并记录 checkpoint_id

前面提过的坑，再强调一次。评估报告里必须包含 thread_id + checkpoint_id，否则“这个用例为什么失败”永远无法复现。

3. LLM-as-Judge 必须做“证据锚定”二次校验

Judge 自己会幻觉。任何依赖 Judge 引用原文的评估，都要加“quote 必须逐字出现在源文本中”的硬校验，否则你的评估分数本身就是幻觉。

4. 稳定性评估的采样数不少于 5，扰动种类不少于 3

单次采样测不出方差。经验值：n_samples >= 5，扰动覆盖“同义改写、错别字、语序调整”三类，才能暴露真实的不稳定性。

5. 把成本指标纳入评估报告，和正确性并列

一个 95% 正确但平均 8 次工具调用的 Agent，可能比 90% 正确但 3 次调用的 Agent 更不可用。成本是可靠性的一部分，因为成本失控本身就是一种不可靠。

6. 多 Agent 场景放弃“轨迹匹配”，改用“约束满足”

不要试图定义“唯一正确的对话路径”。改为定义约束：N 轮内收敛、每个 Agent 不越界、最终结论来自指定 Agent。约束满足的评估器鲁棒性远高于路径匹配。

总结

回到开头那个客服 Agent 的故事。后来我们做了三件事：

  1. 用 checkpointer 旁路导出轨迹，建了 TrajectoryEvaluator，把“冗余调用”从平均 2.3 次压到 0.4 次；
  2. 用带证据锚定的 FaithfulnessJudge，把幻觉率从 8% 降到 1.2%；
  3. 用 StabilityProbe 发现 temperature 是稳定性杀手，调参后轨迹一致性从 0.35 升到 0.9。

投诉率下降 70%。这不是因为我们换了更好的模型，而是因为我们终于能“看见”Agent 的行为了。

最后留一个延伸思考：Agent 评估的终极形态是什么？

我的判断是——评估器本身也会 Agent 化。未来的评估系统不再是“跑一批用例、打个分”，而是一个持续探针 Agent：它主动生成对抗性用例、监控线上轨迹漂移、在指标异常时自动回溯到具体 checkpoint 并生成失败归因。换句话说，你不仅需要一个可靠的 Agent，还需要一个可靠的“评估 Agent”来看着它。 这是下一篇文章想展开的话题。

在那之前，先把本文的三个评估模块跑起来——能被量化的可靠性，才是真正的可靠性。
