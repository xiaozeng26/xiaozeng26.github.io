别再用 v-html 了：从浏览器渲染管线拆解 XSS/CSRF/CSP 的攻防本质

引言

先看一段真实的生产事故复盘：

某电商团队在 Vue 3 的商品详情页里做了一个"富文本规格说明"功能，后端返回一段带样式的 HTML，前端直接

结果：httpOnly 没设的登录态 Cookie 被打包带走，攻击者拿着它批量下单、修改收货地址。更糟的是，这段 payload 被存进了数据库，每个访问该商品页的用户都会中招——这就是存储型 XSS 的典型杀伤链。

很多工程师对 XSS 的认知停在"转义一下尖括号就行了"，对 CSRF 的认知停在"加个 token"，对 CSP 的认知停在"在 nginx 里加个 header"。但这三个东西恰恰是浏览器安全模型的三根支柱，它们各自防守的边界完全不同，混为一谈就会写出"看起来很安全"的漏洞代码。

这篇文章我不打算再复述一遍 OWASP 的 checklist。我想从浏览器渲染管线和同源策略的底层机制出发，讲清楚：

  • 为什么 v-html 的危险不是"渲染了 HTML"，而是"让不可信字符串进入了 DOM 的解析上下文"；
  • CSRF 的本质不是"没有 token"，而是"浏览器会自动携带凭证，而凭证的携带与请求的发起方无关"；
  • CSP 为什么能兜底 XSS，以及为什么 'unsafe-inline' 会让它形同虚设。

一、核心概念：把浏览器想象成一家"自助餐厅"

我用一个贯穿全文的类比来建立直觉。

浏览器 = 一家自助餐厅，页面里的 HTML/JS/CSS 就是顾客能接触到的所有东西。

  • XSS（跨站脚本）：攻击者把一张写着"把收银台的钱交给我"的假菜单，混进了餐厅的官方菜单里。顾客以为是餐厅提供的，照做了。核心问题是"数据和代码混在一起，餐厅分不清哪张是官方菜单"。
  • CSRF（跨站请求伪造）：攻击者在餐厅门口贴了张"凭你的会员卡可免费领饮料"的告示，你拿着自己的会员卡（浏览器自动携带的 Cookie）去柜台，柜台看到有效会员卡就发饮料——但其实这是攻击者想让你触发的操作。核心问题是"凭证跟着人走，但不验证是谁让你来的"。
  • CSP（内容安全策略）：餐厅老板给后厨定了一份"白名单采购清单"：只能从这几家供应商进货，别的一律不收。就算有人塞了假菜单，后厨也不会执行。核心是"用声明式策略约束资源的加载与执行"。

技术定义上：

攻击 利用的信任边界 根本缺陷
XSS 页面内 JS 执行上下文 不可信数据进入了可执行/可解析上下文
CSRF 浏览器对目标站点的自动凭证携带 请求来源（Origin）未参与授权判断
CSP 资源的加载来源 缺少对"允许谁执行什么"的声明式约束

三者不是并列关系，而是纵深防御的三个层次：XSS 是"输入信任"的问题，CSRF 是"请求来源"的问题，CSP 是"运行时兜底"的问题。

二、原理深挖：从渲染管线看 XSS 为什么防不住

2.1 浏览器如何把字符串变成 DOM

要理解 XSS，得先理解浏览器把一段字符串变成可执行页面的过程。简化版渲染管线：

graph TD A[HTML 字节流] --> B[Tokenization 词法分析] B --> C[Tree Construction 建 DOM 树] C --> D[遇到 script 标签: 交给 JS 引擎] D --> E[CSSOM 构建] C --> F[Render Tree] E --> F F --> G[Layout 布局] G --> H[Paint 绘制] H --> I[Composite 合成] D --> J[执行上下文: 可访问 document/cookie/fetch] J --> F

关键点在于：HTML 解析器在 Tree Construction 阶段遇到 、onerror=、javascript: URL）默认被 CSP 拦截，除非显式声明 'unsafe-inline' 或使用 nonce/hash。

看一个严格但可用的策略：

  • 'nonce-{random}'：服务端每次渲染为 截断攻击——生产环境建议用 serialize-javascript 库（它会把 < 转义为 \u003C）。

示例 2：前端 CSRF 防护 —— Double Submit Cookie + Origin 校验

思路：服务端下发一个 csrf Cookie（非 HttpOnly，供 JS 读取），前端在请求头里带上它；服务端比较 header 与 Cookie 是否一致（Double Submit），并额外校验 Origin。这样攻击者既读不到 Cookie（跨站拿不到），也伪造不了 header。

为什么 Double Submit 有效：攻击者从 evil.example 发起请求时，浏览器会带上目标站的 Cookie，但攻击者的 JS 无法读取 bank.example 的 Cookie（同源策略），因此无法在 header 里设置相同的 token。服务端比较两者不一致即拒绝。

局限：如果目标站存在子域 XSS 或 Cookie 注入（如子域可写父域 Cookie），Double Submit 会被绕过。所以生产环境通常叠加服务端会话绑定的 token（如 Spring Security 的 CsrfTokenRepository）。

示例 3：CSP 违规上报 + 渐进式上线

思路：先只上报（Content-Security-Policy-Report-Only），收集真实违规，再逐步收紧到强制策略。这是大厂上线 CSP 的标准姿势，避免一刀切打挂业务。

渐进式策略：

  1. 先 Report-Only 跑 1~2 周，收集所有 blocked-uri；
  2. 分析高频违规来源（往往是第三方 SDK、埋点脚本），逐个用 nonce/hash 或白名单放行；
  3. 切到强制模式，同时保留 report-uri 持续监控；
  4. 定期 review，逐步移除 'unsafe-inline'。

四、方案对比：三层防御的取舍

维度 XSS 防护 CSRF 防护 CSP
主要手段 输出编码 / sanitize / 框架自动转义 SameSite + Token + Origin 校验 声明式资源白名单
生效层次 数据进入 DOM 前 请求到达服务端前/时 浏览器执行资源前
能否兜底 否（一旦漏 sanitize 就中招） 否（依赖浏览器支持） 能（拦截内联脚本执行）
性能开销 低（字符串处理） 低（一次比较） 极低（浏览器原生）
主要坑 上下文混淆（HTML/JS/URL/CSS 不同编码） 子域 Cookie 注入、跨站合法 POST 'unsafe-inline'、nonce 复用、第三方脚本
适用场景 所有渲染不可信内容的场景 所有基于 Cookie 会话的状态变更接口 所有对外 Web 应用

再对比几个常见"替代方案"的局限：

  • 只用 escapeHtml：能防 HTML 注入，但防不住 javascript: URL、onerror 的 URL 上下文；而且它无法处理 里的协议。
  • 只用 CSRF Token：如果 token 通过 URL 传递会泄露到 Referer / 日志；必须放 header 或 POST body。
  • 只用 CSP：CSP 是兜底，不是替代。如果页面本身有 eval、innerHTML 等 sink，CSP 可能被 'unsafe-eval' 或动态加载绕过。

纵深防御的正确姿势：

graph TD A[不可信输入] --> B{输出上下文} B -->|HTML| C[HTML 编码 / DOMPurify] B -->|JS| D[JSON 序列化转义] B -->|URL| E[协议白名单校验] B -->|CSS| F[CSS 转义 / 禁用 expression] C --> G[进入 DOM] D --> G E --> G F --> G G --> H{CSP 拦截} H -->|nonce 匹配| I[执行] H -->|违规| J[blocked + 上报] K[状态变更请求] --> L{Origin 校验} L --> M{SameSite Cookie} M --> N{CSRF Token} N --> O[业务处理]

五、最佳实践与避坑指南

XSS 侧

  1. 默认全部转义，白名单才放行 HTML：React 的 {content}、Vue 的 {{ }} 默认安全；只有确认可信的富文本才用 dangerouslySetInnerHTML / v-html，且必须经过 DOMPurify。
  2. 区分输出上下文：HTML 文本、HTML 属性、JS 字符串、URL、CSS 各有各的编码方式，别用一套 escapeHtml 打天下。比如 URL 里要校验协议，JS 内联要防 。
  3. 前端不信任任何来源：即使服务端做了 sanitize，前端最好再跑一次 DOMPurify（尤其是处理用户上传内容时）。
  4. 警惕 DOM Clobbering：
    可以污染 document.x.y，影响依赖全局变量的脚本。
  5. v-html 的替代：能用组件渲染的结构就别用 HTML 字符串；必须用时，用 sanitize + Trusted Types（见下）。

CSRF 侧

  1. Cookie 三件套：HttpOnly（防 XSS 读 Cookie）+ Secure（仅 HTTPS）+ SameSite=Lax（默认防线）。
  2. Token 放 header，不放 URL：避免 Referer 泄露和日志残留。
  3. GET 不做状态变更：这是 CSRF 最经典的坑，GET /delete?id=1 会被 触发。
  4. 校验 Origin，而非仅 Referer：Referer 可能被隐私模式剥离，Origin 在跨站请求中更可靠。
  5. 子域隔离：把用户内容放在独立子域（如 user-content.example.com），避免子域 XSS 污染主域 Cookie。

CSP 侧

  1. 坚决不用 'unsafe-inline'：用 nonce 或 hash 替代；'unsafe-eval' 也尽量避免。
  2. nonce 必须每次请求随机：复用 nonce 等于没有 nonce。
  3. 'strict-dynamic' 是现代 SPA 的标配：让受信脚本动态加载的子资源也被信任，但注意它会忽略 host 白名单。
  4. report-uri 持续监控：CSP 不是设置了就完事，要持续收集违规并迭代。
  5. frame-ancestors 'none' + X-Frame-Options: DENY：双保险防点击劫持（老浏览器只认后者）。

一个容易被忽视的高级话题：Trusted Types

现代浏览器（Chrome 83+）支持 Trusted Types，它把 innerHTML、eval 等危险 sink 变成"只接受 TrustedHTML 类型"的 API。开启后，字符串直接赋值给 innerHTML 会抛错：

六、总结

回到开头那个事故。如果团队当初做了三件事，损失可以避免：

  1. 服务端对 specHtml 做 DOMPurify 白名单净化（示例 1）——从源头切断注入；
  2. 登录 Cookie 设 HttpOnly + SameSite=Lax——即使有 XSS 也偷不走会话；
  3. 上线严格 CSP（nonce + object-src 'none'）——即使漏网的内联脚本也被拦截。

这三层不是"三选一"，而是"缺一不可"的纵深防御。我见过太多团队把"加了个 CSP header"当作安全工作的终点，结果策略里全是 'unsafe-inline'；也见过把 v-html 当作"只是渲染 HTML 而已"的工程师，直到被存储型 XSS 教育。

最后留一个延伸思考：随着前端框架越来越"组件化"，XSS 的攻击面其实在收缩（因为默认转义覆盖了绝大多数场景），但供应链攻击面在扩大——第三方 SDK、npm 包、CDN 脚本都可能成为注入点。这意味着 CSP 中的 'strict-dynamic' 和 Subresource Integrity（SRI） 会越来越重要。安全不是一次性的 checklist，而是一条持续演进的防线。

记住那个自助餐厅的比喻：XSS 是假菜单混进真菜单，CSRF 是拿你的会员卡替别人买单，CSP 是后厨的采购白名单。三者各守一段边界，才能让餐厅真正安全。
